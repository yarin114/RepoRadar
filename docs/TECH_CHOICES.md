# הצדקת בחירות טכנולוגיות — RepoRadar

מסמך זה מרכז את הנימוקים מאחורי כל בחירה טכנולוגית מרכזית בפרויקט, כולל
ה-trade-offs ושאלות ההמשך הצפויות. הכלל שחוזר בכל הסעיפים: **בחירה טכנולוגית
טובה היא כזו שאפשר להסביר גם את מה שהיא עולה, לא רק את מה שהיא נותנת.**

---

## 1. למה ענן?

**קצר:** שני הרכיבים של המערכת הם תהליכים ארוכי-חיים שצריכים לרוץ 24/7 בלי
תלות במחשב מקומי.

- `bot.py` רץ ב-`run_polling()` — לולאה אינסופית שמושכת הודעות מטלגרם. מחשב
  שנסגר = בוט מת.
- `watcher.py` הוא סוכן אוטונומי (`while True` + `sleep(120)`). כל הרעיון שלו
  הוא שהוא פועל **ביוזמתו**. סוכן אוטונומי שרץ רק כשהלפטופ פתוח הוא לא סוכן —
  הוא סקריפט.
- הענן מספק בנוסף: IP קבוע, restart אוטומטי (`restart: unless-stopped`),
  ניהול סודות מחוץ לקוד, ויעד פריסה אוטומטי מ-CI.

**ההוכחה בפועל:** שלב 7 ב-`deploy/aws/README.md` — "כבה את המחשב האישי שלך
ובדוק שהבוט עדיין מגיב".

**שאלת המשך — "למה לא Raspberry Pi בבית?"**
אפשר, ואפילו זול יותר. אבל אז אני מנהל חשמל, אינטרנט ביתי, NAT ו-uptime בעצמי.
הענן הוא ה-abstraction שמאפשר `docker compose up` על כל instance עם אותה
תוצאה, ומעבר ל-ECS/EKS מחר בלי לגעת בקוד.

## 2. למה AWS?

1. **התאמת העומס למודל התמחור.** תהליך ארוך-חיים שרוב הזמן ישן ומדי פעם עושה
   קריאת רשת — בדיוק הפרופיל של `t2.micro` ב-Free Tier (750 שעות בחודש =
   instance אחד רץ ברצף ללא עלות).
   זו גם הסיבה ש-**Lambda נפסל**: מודל ההרצה שלו הוא event-driven עם timeout;
   long polling ולולאה אינסופית לא מתאימים לו.
2. **AWS הוא הדיפולט בשוק הישראלי** — הידע כאן מתורגם הכי מהר לערך אצל מעסיק.
3. **EC2 ולא ECS/Fargate — במכוון.** רציתי את השכבה שמתחת: התקנת Docker,
   ניהול security group, מפתח SSH, `docker compose logs` על מכונה מרוחקת.
   ECS מסתיר את זה. Fargate מופיע ב-README כצעד הבא — כי עכשיו אני יודע מה
   הוא מסתיר ממני.

**נקודת האבטחה החזקה** (`deploy/aws/README.md` שלב 6): ה-Security Group פותח
**רק port 22, מקור My IP בלבד**. שום פורט לא חשוף לעולם, כי הבוט וה-watcher
עושים רק חיבורים יוצאים לטלגרם ול-Anthropic API.

**שאלת המשך — "ומה בפרודקשן אמיתי?"**
Fargate/EKS במקום EC2 ידני, Secrets Manager או SSM Parameter Store במקום
`.env` על הדיסק, CloudWatch Logs במקום `print()`, ו-Auto Scaling Group.
בלמידה — דווקא לא, כי זה מסתיר את מה שרציתי לראות.

## 3. למה LangChain? מה השימוש שלו כאן?

**התשובה הכנה קודם:** לפרויקט הזה, בגודלו הנוכחי, LangChain אינו הכרחי.
שלושת הסוכנים עושים קריאה בודדת stateless; ה-SDK של `anthropic` היה מספיק
ורזה יותר. בכל זאת נבחר LangChain, ומהסיבות הבאות:

1. **הפשטה אחידה מעל ספקי LLM.** ההערה ב-`agents/review_agent.py` —
   "מייבא את ChatAnthropic במקום ChatOpenAI שהיה מ-learning-agents" — היא
   ההוכחה: החלפת ספק LLM שלם בשינוי import אחד, בלי לגעת בלוגיקת הסוכן.
2. **מודל הודעות אחיד** (`SystemMessage` / `HumanMessage`). שלושת הסוכנים
   חולקים את אותו דפוס, ולכן ה-`Orchestrator` יכול להתייחס לכולם כאל אותו
   אינטרפייס (`.review()`) ולנתב ביניהם ב-dict אחד.
3. **מסלול צמיחה.** memory, retries, tools, RAG, streaming — התשתית כבר שם.
4. **On-ramp ל-LangGraph.** המוצר העיקרי משתמש ב-LangGraph; שניהם חולקים את
   אותם primitives (`langchain-core`, אותם message types).

**Trade-off:** שכבת abstraction ותלויות נוספות תמורת ניידות בין ספקים
והמשכיות לסטאק הקיים.

**שאלת המשך — "אז למה לא LangGraph כאן?"**
LangGraph נועד ל-workflows עם state, מחזורים ותנאי מעבר בין nodes. הסוכנים
כאן stateless לחלוטין, וניתוב שלושה סוכנים לפי `task_type` הוא `if/else`
פשוט — בדיוק מה ש-`orchestrator.route()` עושה. גרף שם היה over-engineering.
**המחיר של abstraction מוצדק רק כשיש מורכבות שהיא מסתירה.**

## 4. למה Claude API — ולא מודל סיני (DeepSeek / Qwen)?

**קצר:** זהו כלי לביקורת קוד. הקוד הוא הקניין הרוחני היקר ביותר של הארגון.
השיקול המכריע הוא ממשל נתונים ובגרות אינטגרציה — לא מחיר לטוקן.

1. **מה עובר בצינור.** RepoRadar שולח **קוד מקור מלא** לספק חיצוני — גם מהבוט,
   וגם אוטומטית מה-watcher בלי אישור פר-קובץ. השאלה הראשונה היא לא "כמה זה
   עולה" אלא מי מחזיק את הנתונים, תחת איזו רשות שיפוט, ומה מדיניות השימור
   והאימון. Anthropic מציעה אי-אימון על נתוני API כברירת מחדל, אפשרויות
   data retention (כולל zero retention), ותאימות ארגונית (SOC 2, DPA).
   עבור ספק הכפוף לרגולציה סינית, זו שאלה שמחלקות Legal סוגרות עוד לפני
   שדיברו על ביצועים.
2. **פרופיל המשימה תואם את החוזק של Claude** — code review, ניתוח ארכיטקטוני
   ו-root-cause analysis הן הקטגוריה שמשפחת Claude מובילה בה בבנצ'מרקים של
   קוד וסוכנים. זה לא סיכום טקסט גנרי שכל מודל עושה סביר.
3. **בגרות האקוסיסטם.** `langchain-anthropic` הוא אינטגרציה רשמית ומתוחזקת —
   שורת קוד אחת, כולל retries וטיפול בשגיאות. חלופות שמסופקות דרך shim
   תואם-OpenAI תלויות בתאימות צד-שלישי שנשברת בשקט.
4. **דיוק ולא יצירתיות, ושליטה בזה.** `temperature=0.2` ל-review ול-debug
   (רוצים עובדות: יש באג או אין), `temperature=0.3` לארכיטקטורה (יש מקום
   לשיקול דעת עיצובי). החלטת מוצר, לא ברירת מחדל.

**הגינות כלפי החלופה:** ל-DeepSeek ול-Qwen יש יתרון אמיתי — מחיר לטוקן
ואופציית self-hosting של משקלים פתוחים. אילו הדרישה הייתה "המידע לא יוצא
מהרשת הארגונית בכלל", Qwen מקומי על GPU היה מועמד רציני ואף עדיף. אבל אז
העלות עוברת מ-API ל-GPU, DevOps ותחזוקה. בהיקף של פרויקט זה, המשוואה נוטה
בבירור ל-API מנוהל.

**חוב טכני ידוע:** הקוד מקבע כרגע `model="claude-sonnet-4-5"` בשלושת הסוכנים —
דור קודם. משפחת Claude 5 היא הנוכחית (`claude-opus-5`, `claude-sonnet-5`),
ו-Sonnet 5 גם חזק יותר וגם זול יותר מ-Sonnet 4.5. עדכון = שלוש מחרוזות.

## 5. למה טלגרם — ולמה בכלל צריך אותו?

### א. למה בכלל ממשק צ'אט

בלי הבוט, RepoRadar הוא `cli.py` — סקריפט מקומי. הבוט הופך אותו ל**שירות**,
ובמדויק יותר הוא ה-**control plane** של המערכת:

- **גישה מכל מקום** — ביקורת קוד מהטלפון, בלי SSH.
- **זהות והרשאה בחינם.** `is_authorized()` משווה `chat_id` יחיד — בלי מערכת
  משתמשים, סיסמאות או OAuth. זה גם שער אבטחה וגם שער עלות: בלעדיו כל אחד
  בעולם צורך את מכסת ה-API שלי.
- **ערוץ פלט לסוכן האוטונומי.** ה-watcher צריך לאן **לדחוף** ממצאים; הודעת
  push היא ה-primitive הנכון, לא קובץ בתיקייה.
- **ההוכחה שהענן חי** — הבוט עונה גם כשהמחשב כבוי.

### ב. למה לא וואטסאפ — הסיבה ארכיטקטונית

| | Telegram Bot API | WhatsApp Cloud API (Meta) |
|---|---|---|
| מודל קבלת הודעות | **long polling** או webhook | **webhook בלבד** |
| דרוש endpoint ציבורי? | **לא** | **כן** — HTTPS + דומיין + TLS |
| פורטים נכנסים ב-EC2 | **אפס** (רק SSH ל-IP שלי) | **443 פתוח לעולם** |
| התחלת עבודה | טוקן מ-BotFather, 2 דקות | Meta Business, אימות עסק, מספר ייעודי |
| עלות | חינם | תשלום לפי conversation |
| הודעות יזומות | חופשי | תבניות מאושרות + חלון שירות של 24 שעות |

שתי מסקנות ישירות:

1. **Long polling הוא הסיבה שה-Security Group סגור לחלוטין.** הבוט יוצר
   חיבורים יוצאים בלבד. וואטסאפ היה מחייב חשיפת 443 לעולם, רכישת דומיין
   וניהול תעודות — והגדלת משטח התקיפה מאפס למשהו.
2. **ה-watcher לא היה עובד על וואטסאפ.** הוא דוחף סיכומים **ביוזמתו**, בלי
   שהמשתמש כתב קודם. חוק ה-24 שעות והתבניות המאושרות של Meta הופכים בדיוק
   את זה לבלתי-אפשרי בלי תהליך אישור עסקי. הדרישה המרכזית של הפרויקט
   מתנגשת חזיתית עם מודל השימוש של וואטסאפ.

*(ספריות לא-רשמיות לוואטסאפ — Baileys, whatsapp-web.js — מפרות את תנאי
השימוש והן הדרך המהירה ביותר לחסימת מספר. לא אופציה.)*

### ג. המחיר של הבחירה

Long polling **לא מתרחב אופקית** — poller אחד לכל טוקן. וזה לא נשאר תיאורטי:
הרצת הבוט במקביל על Docker מקומי, על Kubernetes ועל EC2 החזירה **`409
Conflict`** מטלגרם על `getUpdates`. הפתרון: כיבוי ה-K8s deployment ל-0
replicas והשארת AWS כמופע החי היחיד — וזו הסיבה שה-Deployment של הבוט מקובע
ל-`replicas: 1` עם הערה שמסבירה למה.

**הניסוח לראיון:** "בחרתי long polling כי הוא ביטל את הצורך ב-endpoint ציבורי
והשאיר את השרת עם אפס פורטים חשופים. המחיר הוא שאין scale אופקי — ולא קראתי
על זה, נתקלתי בזה: קיבלתי 409 מטלגרם עם שלושה מופעים חיים. ל-scale אמיתי
הייתי עובר ל-webhook מאחורי Load Balancer — וזה בדיוק מה שרשום ב-'What I'd
do with more time'."
